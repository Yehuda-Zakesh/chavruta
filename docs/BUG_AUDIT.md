# Chavruta Bug Audit

מסמך זה מרכז את ממצאי בדיקת הקוד של פרויקט Chavruta, עם דגש על חיבור באמצעות Bluetooth PAN.
המסמך נכתב כך שכלי AI או מפתח יוכלו להשתמש בו כקלט עבודה: לכל ממצא יש מזהה יציב, חומרה, תנאים, מסלול קוד, השפעה, דרך שחזור, תיקון מוצע ופערי בדיקה.

## 1. תקציר מנהלים

הפרויקט אינו משתמש ב-Bluetooth API ישיר. Bluetooth PAN משמש ככרטיס רשת של Windows, והתקשורת בין שני המחשבים מתבצעת באמצעות UDP broadcast בפורט `45870`.

לכן "באג Bluetooth" בפרויקט הוא בדרך כלל אחד מהבאים:

- Windows לא יצר או לא הפעיל את Bluetooth PAN.
- כרטיס ה-PAN קיים אך כתובתו עדיין `Tentative` או שאי אפשר לקשור אליה סוקט.
- המתאם משדר דרך כרטיס לא נכון או לכתובת broadcast לא נכונה.
- סוקט UDP נסגר בעקבות שגיאת רשת אסינכרונית ואינו מתאושש נכון.
- broadcast מגיע למחשב השני, אך נזרק בגלל חדר, חתימה, זמן או פרוטוקול.
- תוסף אוצריא או המתאם ממשיכים לפעול לאחר שאחד מהם איבד את בעלות מנוע הסנכרון.
- חומת האש חוסמת את הקליטה, או שמנגנון האבחון מציג למשתמש אבחנה שגויה.

### ממצאים בעלי עדיפות ראשונה

1. `LOCAL-ENGINE-001`: `/publish` ו-`/tabs` ממשיכים לשנות ולשדר מצב גם לאחר ש-`claimEngine` דחה את המופע.
2. `PLUGIN-TIMEOUT-001`: כמה קריאות קריטיות ל-Otzaria אינן מוגנות ב-timeout, ולכן המנוע יכול להיתקע ולהפסיק לחדש lease.
3. `API-HTTP-001`: גוף בקשת HTTP נקרא ללא מגבלת גודל או זמן, ולכן תהליך מקומי יכול לגרום לצריכת זיכרון או חיבורי handler ללא גבול.
4. `CONFIG-RACE-001`: כתיבות קונפיגורציה מקבילות אינן מסודרות ואינן אטומיות, ולכן עדכונים יכולים להיאבד או להשאיר JSON פגום.
5. `STARTUP-REG-001`: כשל `reg.exe add` עלול להיראות כהצלחה כאשר רשומת startup ישנה עדיין קיימת.

### ממצאים בעלי עדיפות שנייה

3. `LAN-BROADCAST-001`: חישוב broadcast מניח `/24` לכל רשת שאינה `169.254/16`.
4. `FIREWALL-001`: זיהוי חוקי חסימה תלוי במילה האנגלית `Block`, ולכן עלול להיכשל ב-Windows בשפה אחרת.
5. `INSTALLER-FIREWALL-001`: uninstall מוחק את דגל ה-Firewall גם כאשר מחיקת החוקים נכשלה.

הבדיקה בוצעה על worktree שכבר הכיל שינויים מקומיים רבים. לא נוצרו על ידי הבדיקה הזו תיקוני קוד, ולא בוצע reset או revert. לכן יש לראות במסמך הזה audit של מצב הקבצים שנבדק בפועל, ולא בהכרח של commit נקי אחד.

- סקירת `plugin/js/companion.js` ו-`plugin/js/sync-engine.js`.
- סקירת `companion/lib/firewall_check.dart` והסרת החוקים ב-`installer/chavruta.iss`.
- סקירת הבדיקות הקיימות.

### אימות אוטומטי שבוצע

- `node --check` עבור `plugin/js/sync-engine.js`, `plugin/js/companion.js` ו-`plugin/js/app.js`: עבר.

הבדיקות האלו מאשרות שהקוד מתקמפל ושההתנהגויות שכבר נבדקו תקינות. הן אינן מוכיחות חיבור Bluetooth PAN אמיתי בין שני מחשבי Windows.

## 3. מודל החיבור הרלוונטי ל-Bluetooth PAN

המסלול הוא:

```text
Otzaria WebView
    |
    | HTTP loopback, ports 45871-45875
    v
Chavruta Companion
    |
    | UDP broadcast, port 45870
    v
Windows network interfaces
    |
    | Bluetooth PAN / Wi-Fi / Ethernet / Wi-Fi Direct
    v
Chavruta Companion במחשב השני
```

ב-Bluetooth PAN המתוכנן, שני המחשבים בדרך כלל מקבלים כתובות `169.254.x.x`. במקרה הזה ה-broadcast הצפוי הוא `169.254.255.255`.

המתאם מנסה לקשור socket שידור נפרד לכל כתובת IPv4 מקומית. הדבר חשוב במיוחד ב-Windows, שבו יכולים להיות כמה כרטיסים וירטואליים עם כתובות `169.254.x.x`, כולל Bluetooth PAN ו-Wi-Fi Direct. socket כללי שקשור ל-`0.0.0.0` עלול לצאת דרך כרטיס אחר מזה שבו נמצאת החברותא.

## 4. ממצאים מפורטים

## `LOCAL-ENGINE-001` — מופע שאיבד בעלות עדיין יכול לפרסם מיקום וטאבים

- **חומרה:** גבוהה.
- **סוג:** באג התנהגותי, race בין מופעי התוסף.
- **רלוונטיות ל-Bluetooth:** גבוהה בעקיפין. בזמן ניתוק/חיבור מחדש או החלפת מופע רקע/לשונית, נוצרים שידורים כפולים או מצב מקומי לא נכון, שנראים ככשל סנכרון ברשת.
- **קובץ:** [`companion/lib/local_api.dart`](../companion/lib/local_api.dart#L240-L290).

### הקוד המעורב

ב-`_handlePublish` וב-`_handleTabs` מתקבלת `instance`, ונקראת:

```dart
hub.claimEngine(instance);
```

אבל ערך ההחזרה אינו נבדק. לאחר מכן הקוד תמיד ממשיך אל:

```dart
await hub.publishLocal(location);
await hub.publishLocalDesk(...);
```

לעומת זאת, `/events` כן בודק את תוצאת `claimEngine` ומחזיר `engineMine: false` כאשר המופע נדחה.

### תנאי הפעלה

1. מופע א' מחזיק את המנוע.
2. מופע ב' עולה או משתלט, כך שה-`SyncHub` דוחה את א'.
3. בקשת `/publish` או `/tabs` שכבר הייתה בתעופה, או בקשה שנשלחה באיחור, מגיעה עם `instance` של א'.
4. `claimEngine` מחזיר `false`, אך הפעולה עדיין נרשמת ומועברת ל-transport.

### השפעה

- שני מופעים יכולים לשדר מיקום במקביל.
- מופע שכבר אינו אמור לנהל סנכרון יכול לעדכן `_localLocation` או `_localTabs`.
- במעבר ownership, השידור האחרון אינו בהכרח מגיע מהמופע שמציג את המסך העדכני.
- במצב Bluetooth עם reconnect, שבו ה-lease והלולאות רגישים לזמן, הסיכוי לפגוש את race גדל.

### תיקון מומלץ

להשתמש ב-`refreshEngine` או ב-check חד-משמעי לפני שינוי state, ולא להסתמך על `claimEngine` שמותר לו לרכוש בעלות. לדוגמה, כאשר `instance` אינו ריק:

1. לבדוק שהמופע הוא הבעלים.
2. אם אינו הבעלים, להחזיר תשובה מפורשת עם `engineMine: false` ולא לקרוא ל-`publishLocal` או `publishLocalDesk`.
3. להחליט האם endpoint צריך להחזיר `409 Conflict` או תשובת JSON תקינה עם `broadcast: false`; חשוב שהחוזה יהיה אחיד בתוסף.

### בדיקה חסרה

בדיקת integration צריכה:

- להעניק ownership ל-`background:x`.
- להעניק ownership ל-`foreground:y` או לוודא שהוא נדחה לפי הכלל.
- לשלוח `/publish` ו-`/tabs` בשם המופע שנדחה.
- לוודא שלא נשלחה הודעה, שלא השתנה `_localLocation` ושלא השתנה `_localTabs`.

## `PLUGIN-TIMEOUT-001` — קריאות קריטיות ל-Otzaria עלולות לתקוע את לולאת הסנכרון

- **חומרה:** גבוהה.
- **סוג:** hang / אובדן lease.
- **רלוונטיות ל-Bluetooth:** גבוהה בעקיפין. Bluetooth PAN יכול להיות איטי או לא יציב בזמן התחברות, אך התקיעה מתרחשת בצד התוסף וגורמת למשתמש לחשוב שהקישור מת.
- **קובץ:** [`plugin/js/sync-engine.js`](../plugin/js/sync-engine.js#L155-L160), [`plugin/js/sync-engine.js`](../plugin/js/sync-engine.js#L560-L610), [`plugin/js/sync-engine.js`](../plugin/js/sync-engine.js#L737-L760).

### הקוד המעורב

קיימת עטיפה מוגנת:

```javascript
function callWithTimeout(method, args) {
  return Promise.race([...]);
}
```

אבל המסלולים הבאים קוראים ישירות ל-`Otzaria.call`:

- `currentLocation()` קוראת ל-`reader.getCurrentRef`.
- `applyDeskPlan()` קוראת ל-`reader.openBook` עבור פתיחה.
- `applyDeskPlan()` קוראת ל-`reader.openBook` כדי לחזור למקום הקודם.
- `applyRemote()` קוראת ל-`reader.openBook`.

### תנאי הפעלה

1. `Otzaria.call` עבור אחת מהמתודות לא פותרת Promise וגם לא דוחה אותו.
2. `setOwner(true)` מחכה ל-`republishCurrent()`.
3. לולאת `loop()` אינה חוזרת ל-`Companion.events`.
4. בצד המתאם, ה-engine lease מפסיק להתחדש.

### השפעה

- המנוע מפסיק לשלוח `/events`.
- אחרי `engineLeaseTimeout` מופע אחר יכול לקבל ownership.
- המופע התקוע עדיין מחזיק listener או state פנימי, ועלול לחזור לפעול אם הקריאה תשתחרר מאוחר יותר.
- משתמש רואה שאין עדכון מיקום או שהחיבור נעלם, אף שסוקט ה-UDP עצמו תקין.

### תיקון מומלץ

להשתמש ב-`callWithTimeout` בכל קריאות ה-reader שעלולות להיתקע. בפרט:

- `currentLocation()`.
- שתי הקריאות ל-`reader.openBook` בתוך `applyDeskPlan()`.
- הקריאה ל-`reader.openBook` בתוך `applyRemote()`.

רצוי גם להוסיף cancellation או token check אחרי כל `await`, כדי שמופע שאיבד ownership לא ימשיך לבצע פעולה שהתחילה לפני האובדן.

### בדיקה חסרה

Mock של `Otzaria.call` צריך להחזיר Promise שאינו נפתר. לאחר יותר מ-`API_TIMEOUT_MS` יש לוודא ש:

- הקריאה מסתיימת בשגיאה מבוקרת.
- הלולאה חוזרת לנסות `/events`.
- ה-status מציג כשל ולא נשאר תקוע.
- ownership מתחדש או שמופע אחר יכול להשתלט בלי שני מנועים פעילים.

## `API-HTTP-001` — גוף HTTP ללא מגבלת גודל או זמן

- **חומרה:** בינונית.
- **סוג:** resource exhaustion / denial of service מקומי.
- **רלוונטיות ל-Bluetooth:** בינונית בעקיפין. הבעיה אינה ב-UDP, אך המתאם עלול להיתקע או לצרוך משאבים בזמן אבחון חיבור Bluetooth.
- **ודאות:** גבוהה.
- **קובץ:** [`companion/lib/local_api.dart`](../companion/lib/local_api.dart#L471-L484).

### הקוד המעורב

`_readJsonBody` קורא את כל גוף הבקשה באמצעות `utf8.decoder.bind(request).join()`.
אין מגבלת bytes, אין בדיקה מוקדמת של `Content-Length`, ואין timeout לקריאה מחיבור chunked או לחיבור שנפתח אך אינו מסיים את הגוף.

### תנאי הפעלה

כל תהליך מקומי שיכול להתחבר ל-`127.0.0.1` יכול לפתוח POST, לשלוח גוף גדול מאוד, או לשלוח נתונים באיטיות ולעולם לא לסגור את הבקשה. סינון כותרות דפדפן אינו מונע זאת.

### השפעה

- `join()` עלול להחזיק מחרוזת גדולה מאוד בזיכרון.
- handlers רבים יכולים להישאר תלויים לאורך זמן.
- עומס מקומי יכול לפגוע ב-`/events`, ב-heartbeat ובפעולות Bluetooth PAN.

### תיקון מומלץ

- להגדיר `maxApiBodyBytes` קטן המתאים לגופים הלגיטימיים.
- לדחות `Content-Length` גדול מדי לפני קריאה.
- לספור bytes בפועל גם בגוף chunked ולסגור את הבקשה כאשר עוברים את הגבול.
- להוסיף timeout לקריאת body.
- להחזיר `413 Payload Too Large` לגוף גדול ו-`408 Request Timeout` ל-body שלא הושלם.
- להפריד את timeout של `/events` מה-timeout של body רגיל.

### בדיקה חסרה

- גוף בגודל `maxApiBodyBytes + 1` מחזיר 413.
- גוף chunked גדול נדחה גם בלי `Content-Length`.
- גוף איטי שלא מסתיים נקטע בזמן.
- אחרי בקשה בעייתית המתאם עדיין עונה ל-`/hello` ול-`/events`.

## `CONFIG-RACE-001` — כתיבות קונפיגורציה מקבילות עלולות לאבד עדכון או להשאיר JSON פגום

- **חומרה:** בינונית.
- **סוג:** race / persistence corruption.
- **רלוונטיות ל-Bluetooth:** גבוהה בעקיפין. אובדן `roomCode` אחרי restart ייראה כניתוק Bluetooth או כחדר שאינו מוצא את הצד השני.
- **ודאות:** גבוהה מבחינת היעדר serialization ו-atomic write; חומרת השחיתות בפועל תלויה בהתנהגות מערכת הקבצים.
- **קבצים:** [`companion/lib/config.dart`](../companion/lib/config.dart#L216-L230), [`companion/lib/sync_hub.dart`](../companion/lib/sync_hub.dart#L291-L323).

### הקוד המעורב

`CompanionConfig.save()` כותב ישירות ל-`config.json`. אין queue, lock, revision או כתיבה לקובץ זמני עם rename.
כמה endpoints יכולים לשנות שדות שונים ולקרוא ל-`save()` במקביל, משום שה-`await` בתוך השמירה מאפשר לכתיבות להצטלב.

### תנאי הפעלה

1. לשלוח שתי בקשות שינוי כמעט באותו זמן.
2. כל handler משנה שדה אחר וקורא `await config.save()`.
3. פעולות filesystem מסתיימות בסדר שונה, או שאחת הכתיבות נקטעת.

### השפעה

- עדכון מאוחר יכול לדרוס עדכון אחר.
- קוד חדר, שם מכשיר או הגדרת sync יכולים להיעלם אחרי restart.
- interruption בזמן כתיבה עלול להשאיר JSON חלקי.
- `load()` תופס שגיאה ובונה קונפיגורציה חדשה, ולכן אפילו `deviceId` עלול להשתנות.

### תיקון מומלץ

- לרכז את כל הכתיבות בתור אסינכרוני יחיד לכל `CompanionConfig`.
- לכתוב לקובץ זמני באותה תיקייה ואז לבצע rename אטומי ל-`config.json`.
- לשמור backup קטן של הקובץ הקודם לצורך recovery.
- להחזיר שגיאת persistence ברורה ל-API במקום להציג הצלחה לאחר כשל.

### בדיקה חסרה

- להריץ מספר `save()` במקביל עם שדות שונים ולוודא שכל הערכים נשמרים.
- לדמות כשל באמצע write ולוודא שהקונפיגורציה הקודמת נשארת תקינה.
- לוודא ש-`deviceId` אינו משתנה בעקבות קונפיגורציה פגומה.
- לבדוק ששינוי חדר במקביל לשינוי שם אינו מאבד אחד מהם.

## `STARTUP-REG-001` — כשל `reg.exe add` עלול להיראות כהצלחה

- **חומרה:** בינונית.
- **סוג:** false success / state reporting.
- **רלוונטיות ל-Bluetooth:** נמוכה ישירות, אך המתאם עלול לא לעלות אחרי restart ולכן Bluetooth PAN והסנכרון לא יופעלו כלל.
- **ודאות:** גבוהה.
- **קובץ:** [`companion/lib/startup_registration.dart`](../companion/lib/startup_registration.dart#L132-L170).

### הקוד המעורב

`setEnabled(true)` מפעיל `_runReg([... 'add' ...])`, אך אינו בודק את `ProcessResult.exitCode`. אחר כך הוא קורא ל-`read()` ומסיק הצלחה מהמצב שנמצא ברישום.

### תנאי הפעלה

1. קיימת כבר רשומת startup ישנה בשם `ChavrutaCompanion`.
2. הרשומה הישנה עדיין מצביעה למיקום כלשהו.
3. פקודת `reg add` נכשלת בגלל policy, הרשאות, registry issue או כשל תהליך.
4. `read()` רואה את הרשומה הישנה ומחזיר `enabled: true`.

### השפעה

- המשתמש מבקש להפעיל startup אך הנתיב החדש אינו נכתב.
- ה-UI יכול להציג שהפעולה הצליחה.
- אחרי reboot Windows מפעיל את הרשומה הישנה, או שאינו מפעיל מתאם תקין.
- כאשר הבעיה מתרחשת במקביל ל-Bluetooth PAN, המשתמש יפרש זאת ככך שהחיבור לא חוזר אחרי הפעלה מחדש.

### תיקון מומלץ

- לבדוק `exitCode` אחרי כל `reg add` ו-`reg delete`.
- במקרה של כשל, לא לבצע `read()` כאילו הוא הוכחת הצלחה.
- להשוות את הערך הרשום לערך המבוקש, כולל command מלא, ולא רק את קיום הערך.
- להחזיר `supported: true`, `enabled` לפי המצב האמיתי ו-`reason` מפורש.
- לתעד exit code ו-stderr בלוג, בלי לחשוף מידע מיותר.

### בדיקה חסרה

- mock שבו `reg add` מחזיר exit code שאינו אפס ורשומה ישנה קיימת.
- mock שבו `reg add` מצליח אך Windows משאיר ערך שונה.
- כשל `reg delete` כאשר הערך קיים.
- בדיקה שה-API אינו מחזיר הצלחה מדומה.

## `LAN-BROADCAST-001` — חישוב broadcast מניח מסכת `/24`

- **חומרה:** בינונית.
- **סוג:** כשל גילוי תלוי subnet.
- **רלוונטיות ל-Bluetooth:** בינונית. Bluetooth PAN המתועד משתמש ב-`169.254/16`, והוא מטופל נכון; אך המימוש מצהיר שכל IPv4 אחר עובד, ולכן הכשל רלוונטי ל-Wi-Fi, hotspot, Ethernet או PAN עם מסכה שונה.
- **קובץ:** [`companion/lib/lan_transport.dart`](../companion/lib/lan_transport.dart#L660-L668).

### הקוד המעורב

```dart
if (octets[0] == '169' && octets[1] == '254') {
  return linkLocalBroadcast;
}
return '${octets[0]}.${octets[1]}.${octets[2]}.255';
```

הפונקציה מקבלת רק כתובת, לא netmask ולא prefix length. לכן כל רשת שאינה `169.254/16` מחושבת כאילו היא `/24`.

### תנאי הפעלה

לדוגמה:

- כתובת מקומית: `10.20.1.7`.
- מסכה בפועל: `/16`.
- broadcast נכון: `10.20.255.255`.
- broadcast שהקוד שולח אליו: `10.20.1.255`.

במקרה אחר של `/20`, גם הכתובת המחושבת עלולה להיות שגויה.

### השפעה

הודעות לא מגיעות לכל המחשבים באותה רשת. התוסף עשוי להציג:

- שידור תקין וחזרה מקומית של המנה.
- אפס `datagramsFromOthers`.
- אבחנה כאילו אין קישור או שהצד השני כבוי.

זו אבחנה מטעה משום שהבעיה היא יעד broadcast שגוי.

### תיקון מומלץ

לאסוף מ-`NetworkInterface` גם את ה-prefix או ה-netmask, אם ה-API מאפשר זאת בפלטפורמה הנתמכת, ולחשב broadcast באמצעות פעולות bitwise על כתובת ומסכה.

אם Dart אינו חושף netmask בצורה מספקת בכל Windows, יש שתי חלופות סבירות:

1. להשתמש ב-Windows API או תהליך מערכת שמחזיר interface address ומסכה.
2. להוסיף יעד unicast/peer discovery לצד broadcast, או להגדיר במפורש אילו מסכות נתמכות ולהציג מגבלה אמיתית למשתמש.

אין לתקן את זה באמצעות שינוי קבוע נוסף ל-`/24`; זו רק החלפת הנחה אחת באחרת.

### בדיקה חסרה

פונקציית חישוב טהורה צריכה לקבל כתובת ומסכה ולבדוק לפחות:

- `/8`, `/16`, `/20`, `/24`, `/30`.
- כתובות גבול.
- מספר interfaces עם מסכות שונות.
- שמירה על ההתנהגות המיוחדת של `169.254/16`.

## `FIREWALL-001` — חוק Block בשפה שאינה אנגלית מזוהה כהיתר

- **חומרה:** בינונית.
- **סוג:** אבחון שגוי; עלול להסתיר חסימה אמיתית.
- **רלוונטיות ל-Bluetooth:** גבוהה. Bluetooth PAN תלוי בקליטת UDP נכנסת בפורט `45870`, ולכן חוק חסימה הוא סיבה ישירה לכך ששני המתאמים לא ימצאו זה את זה.
- **קובץ:** [`companion/lib/firewall_check.dart`](../companion/lib/firewall_check.dart#L145-L151).
- **טסט שממחיש את הבעיה:** [`companion/test/firewall_check_test.dart`](../companion/test/firewall_check_test.dart#L108-L116).

### הקוד המעורב

```dart
final _actionLine = RegExp(r'^\s*action\s*:\s*(\S+)', multiLine: true);

bool _isBlockingRule(String block) {
  final match = _actionLine.firstMatch(block.toLowerCase());
  if (match == null) return false;
  return match.group(1) == 'block';
}
```

כאשר `Action` או הערך `Block` מתורגמים על ידי Windows, ה-regex לא מזהה אותם. בהיעדר זיהוי חסימה, `_verdictFor` עלול להחזיר `allowed` עבור חוק שאינו מתיר בפועל.

### תנאי הפעלה

1. קיים חוק Firewall עבור executable של Chavruta.
2. החוק הוא Block, או שקיימים Allow ו-Block יחד.
3. Windows מציג את שדה הפעולה בשפה שאינה אנגלית, למשל `Aktion` במקום `Action` או ערך מתורגם.
4. parser לא מזהה את החסימה.

### השפעה

המתאם עלול להציג שאין בעיית Firewall, אף ש-Windows חוסם את הקליטה. המשתמש ימשיך לבדוק Bluetooth, קוד חברותא או את הצד השני, במקום להסיר את חוק החסימה.

### תיקון מומלץ

לא להסתמך על טקסט אנושי מתורגם של `netsh`. עדיף:

- להשתמש ב-Windows Firewall COM API או PowerShell עם output מובנה ויציב.
- או לקרוא חוק לפי שם/תוכנית ולבקש שדה שאינו תלוי שפה.
- אם חייבים parser של `netsh`, לזהות כמה שפות ולנקוט ברירת מחדל שמרנית: פעולה לא ידועה לא תיחשב כהיתר ודאי.

חשוב להפריד בין:

- `allow` מפורש.
- `block` מפורש.
- `unknown`.

`unknown` אינו צריך להפוך אוטומטית ל-`true`.

### בדיקה חסרה/בעייתית

הטסט המתורגם ב-`firewall_check_test.dart` מצפה ל-`true` כאשר `Action` הוחלף ב-`Aktion`. זה מנציח את ההתנהגות המסוכנת. יש לשנות אותו כך שיבדוק `false` או תוצאה של `unknown`, לפי חוזה חדש.

## `INSTALLER-FIREWALL-001` — uninstall מוחק את מצב ההתקנה גם אם מחיקת החוקים נכשלה

- **חומרה:** נמוכה-בינונית.
- **סוג:** כשל cleanup ושאריות הרשאה במערכת.
- **רלוונטיות ל-Bluetooth:** בינונית. חוקי Firewall נשארים קשורים ליישום שכבר הוסר, ועלולים לבלבל התקנה עתידית או להותיר הרשאות/חסימות ישנות.
- **קובץ:** [`installer/chavruta.iss`](../installer/chavruta.iss#L264-L285).

### הקוד המעורב

`RemoveFirewallRules` בונה פקודת `netsh`, קורא ל-`ShellExec`, אך אינו משתמש ב-`ResultCode` כדי להחליט אם המחיקה הצליחה. לאחר מכן הוא מוחק את `FirewallFlag`.

### תנאי הפעלה

- המשתמש דוחה UAC.
- `netsh` נכשל.
- אחד מהחוקים לא קיים או שמחיקתו נכשלה.
- uninstall רץ בהקשר ללא הרשאות מתאימות.

### השפעה

בפעם הבאה אין דגל שמורה ל-uninstaller לנסות cleanup. החוקים יכולים להישאר במערכת ללא הודעה למשתמש.

### תיקון מומלץ

- לבדוק `ShellExec` ואת `ResultCode`.
- למחוק `FirewallFlag` רק כאשר שתי מחיקות החוקים הצליחו, או כאשר אומת שאין יותר חוקים.
- במקרה של כשל, לשמור את הדגל ולהציג הודעה ברורה או לרשום cleanup retry.
- להגדיר התנהגות מפורשת ל-uninstall שקט, שבו אין אפשרות להציג UAC.

### בדיקה חסרה

בדיקות installer צריכות לכסות:

- UAC שאושר.
- UAC שנדחה.
- `netsh` עם exit code שאינו אפס.
- חוק אחד קיים והשני חסר.
- uninstall חוזר לאחר כשל ראשון.

## 5. סיכונים ופערים נוספים שדורשים בדיקה

הסעיפים הבאים אינם מסווגים כאן כבאגים מאומתים באותה רמת ודאות, אך הם נקודות סיכון שחשוב לסגור בבדיקות או בתיעוד.

### `RISK-BT-001` — אין בדיקת integration אמיתית של Bluetooth PAN

הטסטים משתמשים ב-fake transport, loopback או כתובות מדומות. אין בדיקה שבה:

- שני Windows hosts מחוברים ב-Bluetooth PAN.
- לכל צד יש כתובת `169.254.x.x`.
- שני המתאמים מאזינים באותו `45870`.
- מנות presence/location/desk עוברות בשני הכיוונים.
- חיבור ה-PAN נופל וחוזר.

בלי בדיקה כזו, אי אפשר להוכיח שההתנהגות של `RawDatagramSocket.bind` ושל broadcast זהה לזו שההנחות בקוד מתארות.

### `RISK-BT-002` — sleep/wake ושינוי כתובת אינם נבדקים מקצה לקצה

יש טסטים ל-`reportSocketFailure` ולשינוי רשימת כתובות, אך אין תרחיש Windows אמיתי שבו:

1. המחשב נכנס לשינה.
2. Bluetooth PAN מתנתק.
3. כתובת או interface נעלמים.
4. המחשב מתעורר.
5. ה-PAN מתחבר מחדש.
6. המתאם מזהה את הכרטיס ומתחיל לשדר שוב.
7. הצד השני מזהה presence בתוך זמן סביר.

יש לאמת גם שהשידור אינו יוצא דרך כרטיס וירטואלי אחר וש-`isSending` חוזר לערך הנכון.

### `RISK-BT-003` — קישור שנראה חי בצד אחד בלבד

המערכת משתמשת ב-loopback של broadcast ובמוני `datagramsReceived`/`datagramsFromOthers`. כדאי לבדוק בפועל מצבים שבהם:

- השידור יוצא אך אינו חוזר מקומית.
- הקליטה עובדת אך השידור דרך PAN נכשל.
- socket הקליטה חי אך socket שידור מסוים נסגר.
- יש כמה כרטיסים, ורק אחד מחובר לחברותא.

צריך לוודא שה-UI מציג את השילוב הנכון ולא מסיק מכל מונה מסקנה חזקה מדי.

### `RISK-PROTOCOL-001` — גודל הודעה ו-MTU

יש חלוקה לפי `maxDeskPayloadBytes = 1200`, אך עדיין קיימים סיכונים:

- פריט יחיד ארוך מאוד נשלח גם אם הוא חורג מהתקציב.
- אין בדיקת גודל קשיחה ב-`encode` לפני שליחה.
- מנות של location או presence יכולות לגדול בגלל `senderName` ארוך.
- אין test שמודד את גודל כל סוג הודעה מול גבול שנבחר.

כדאי להגדיר מגבלות אורך על `deviceName`, `bookId`, `ref` ולכל הודעה, או להוסיף fragmentation ברמת האפליקציה אם יש צורך בתוכן ארוך.

### `RISK-PROTOCOL-002` — שדות קלט עם גבולות חלשים

`SyncLocation.fromJson` ו-`DeskEntry.fromJson` בודקים סוגים וערכים בסיסיים, אך אין גבול מפורש לאורך מחרוזות. במערכת שנגישה לכל מי שבאותה רשת, הודעה חתומה עדיין יכולה להיות גדולה מאוד אם למי שיודע את קוד החדר יש יכולת לשלוח payload חריג.

יש להוסיף גבולות ל:

- `bookId`.
- `senderName`.
- `ref`.
- `by`.
- גודל JSON כולל לפני parsing או מיד אחריו.

### `RISK-ENGINE-002` — async שהתחיל לפני איבוד ownership עלול להשלים מאוחר

גם לאחר הוספת timeout, `applyDeskPlan`, `applyRemote`, `scanDesk` ו-`setOwner` מכילים רצפי `await`. יש token checks בחלק מלולאת המנוע, אך יש לבדוק כל פעולה שמבצעת שינוי באוצריא אחרי איבוד ownership.

תרחיש חשוב:

1. מופע א' מתחיל `reader.openBook`.
2. מופע ב' מקבל ownership.
3. מופע א' מסיים את הקריאה.
4. מופע א' ממשיך לפתוח/לסגור/לדווח למרות שכבר אינו הבעלים.

הגנה צריכה להיות ממש לפני פעולת side effect, לא רק אחרי ה-`await` הקודם.

### `RISK-API-001` — חוזה ownership אינו אחיד בכל endpoints

`/events` מחזיר `engineMine: false`, בעוד `/publish` ו-`/tabs` מתנהגים כאילו אין rejection. יש להגדיר חוזה אחיד לכל endpoint שנושא `instance`:

- האם מופע לא-בעלים מקבל HTTP `409`?
- האם התשובה היא `200` עם `engineMine: false`?
- האם בקשה בלי `instance` היא API legacy מותר או מסלול שצריך להפריד?

חוזה לא אחיד מקשה על התוסף לזהות מצב race ומקשה על בדיקות.

## 6. תרחישי שחזור מומלצים

### תרחיש A — Bluetooth PAN אינו מחובר

- Bluetooth מותאם אך לא בוצעה "הצטרפות לרשת אישית".
- Windows עדיין מציג interface או כתובת link-local.
- `NetworkInterface.list` מחזיר את הכתובת.

ציפייה:

- `routes` מכיל את הכתובת.
- `isSending(local)` הוא `false`.
- socket הקליטה נשאר חי.
- אין restart loop.
- ה-UI אומר שהכרטיס אינו משדר, ולא שחומת האש בהכרח אשמה.

### תרחיש B — Bluetooth PAN מחובר בשני הצדדים

- צד א': `169.254.a.b`.
- צד ב': `169.254.c.d`.
- בשני הצדדים מופיע broadcast `169.254.255.255`.
- `isSending` הוא `true` בשני הצדדים.
- מוני `datagramsFromOthers` גדלים.
- `peer joined` מופיע בתוך מחזור presence אחד.

### תרחיש C — ניתוק והתאוששות

- להפעיל סנכרון.
- לנתק את Bluetooth PAN או להעביר את המחשב לשינה.
- לבדוק ש-`isBound` הופך ל-`false` כאשר socket הקליטה נופל.
- לחבר מחדש.
- לבדוק שה-socket קם, המסלולים מתעדכנים, `isSending` מתעדכן, ונוכחות נשלחת מיד.

### תרחיש D — שני מופעי תוסף

- להפעיל מופע רקע ומופע לשונית.
- להעביר ownership ביניהם.
- לשלוח בקשות publish/tabs משני המופעים בזמן המעבר.
- לוודא שרק הבעלים משנה state ומשדר.

### תרחיש E — Firewall בשפה שאינה אנגלית

- ליצור Allow ו-Block עבור אותו executable.
- להריץ Windows בשפה שבה שדות `netsh` מתורגמים.
- לוודא שה-parser מזהה חסימה או מחזיר `unknown`, אך לעולם לא `allowed` ודאי בלי הוכחה.

## 8. Definition of Done מומלץ

העבודה על תיקון האזור הזה תיחשב שלמה רק כאשר כל התנאים הבאים מתקיימים:

- מופע שאינו בעלים אינו יכול לשדר או לשנות state דרך `/publish` ו-`/tabs`.
- כל `Otzaria.call` במסלול הסנכרון הקריטי מוגן ב-timeout מוגדר.
- אחרי timeout או איבוד ownership אין side effect מאוחר מהמופע הישן.
- broadcast מחושב לפי netmask אמיתי, או שמגבלת `/24` מתועדת ונאכפת במפורש.
- זיהוי Firewall אינו תלוי במילה אנגלית אחת ואינו מסווג unknown כהיתר.
- uninstall משאיר retry state כאשר cleanup נכשל.
- קיימת בדיקת integration אמיתית עבור Bluetooth PAN בשני הכיוונים.
- קיימת בדיקת sleep/wake או לפחות ניתוק/חיבור מחדש של interface ב-Windows.
- קיימות בדיקות לכל ה-races של ownership.
- כל 202 הבדיקות הקיימות ממשיכות לעבור, ונוספות בדיקות ממוקדות לכל ממצא.

## 9. סיכום

החלק המרכזי של תשתית ה-Bluetooth PAN כבר מתוכנן סביב הבעיות הנכונות: שימוש בכתובת `169.254.255.255`, socket שידור נפרד לכל כתובת מקומית, טיפול ב-socket שנפל, ו-diagnostics שמפרידים בין כרטיס שאינו משדר לבין Firewall או קוד חדר שגוי.

עם זאת, קיימים שני כשלים שיכולים לפגוע ישירות באמינות הסנכרון בלי קשר לאיכות קישור ה-Bluetooth: ownership שאינו נאכף ב-`/publish` וב-`/tabs`, וקריאות reader ללא timeout. בנוסף, חישוב `/24` מגביל רשתות IPv4 אחרות, ו-parser של Firewall עלול להסתיר חסימה במערכות Windows שאינן באנגלית.

העובדה שכל הבדיקות הקיימות עוברות אינה סותרת את הממצאים: רובם נמצאים בגבולות אינטגרציה, בתרחישי race, בתלות ב-Windows ובשפות מערכת, או במסלולים שאין להם test ייעודי.

## 10. אימות הממצאים וטיפול בהם

הסעיף הזה נוסף אחרי בדיקת כל ממצא מול הקוד בפועל. הוא מתעד גם את מה שתוקן, גם את מה שנמצא לא מדויק, וגם את מה שנשאר בכוונה.

| מזהה | האם אמיתי | מה נעשה |
|---|---|---|
| `LOCAL-ENGINE-001` | כן | תוקן |
| `PLUGIN-TIMEOUT-001` | כן | תוקן |
| `API-HTTP-001` | כן, חומרה נמוכה מהמתואר | תוקן |
| `CONFIG-RACE-001` | חלקית | תוקן מה שנכון |
| `STARTUP-REG-001` | כן | תוקן |
| `INSTALLER-FIREWALL-001` | כן | תוקן |
| `LAN-BROADCAST-001` | ההנחה נכונה, המסקנה לא | לא שונה |
| `FIREWALL-001` | התיאור נכון, ההמלצה שגויה | לא שונה |

### מה תוקן

- **`LOCAL-ENGINE-001`.** `/publish` ו-`/tabs` בודקים בעלות **לפני** כל שינוי מצב, ומופע שנדחה מקבל `200` עם `engineMine: false` — אותו חוזה כמו `/events`, וזה סוגר גם את `RISK-API-001`. גוף בלי `instance` ממשיך להתקבל.
- **`PLUGIN-TIMEOUT-001`.** `currentLocation` וכל שלוש הקריאות ל-`reader.openBook` עברו ל-`callWithTimeout`, וכך גם `storage.set`. שלוש הקריאות שנשארו ישירות הן הודעות UI שאיש אינו ממתין להן, ולכן אינן יכולות לתקוע את הלולאה. בנוסף נבדקת הבעלות ממש לפני כל פתיחת ספר ולפני הניווט — זה חלק מ-`RISK-ENGINE-002`.
- **`API-HTTP-001`.** תקרת `maxApiBodyBytes` (256KB) שנאכפת גם בלי `Content-Length`, ו-`apiBodyTimeout` של עשר שניות חוסר-פעילות. הערה שנמצאה בבדיקה: כשגוף הבקשה לא הושלם, `HttpServer` של Dart סוגר את החיבור ואינו שולח את ה-408 שנכתב. מה שמשתחרר הוא ה-handler, וזה העיקר.
- **`CONFIG-RACE-001`.** הכתיבה עברה לקובץ זמני והחלפה בשם, והשמירות עומדות בתור אחד. **הטענה על "עדכון שדורס עדכון" אינה נכונה**: כל השדות יושבים באותו אובייקט בזיכרון, ולכן כל `save()` כותב תמונה שלמה ואף שדה אינו הולך לאיבוד. מה שכן היה אמיתי הוא הכתיבה הלא-אטומית: קובץ חתוך פירושו `deviceId` חדש וקוד חדר שנעלם.
- **`STARTUP-REG-001`.** קוד היציאה של `reg add` נבדק. כישלון מדווח ככבוי עם קוד היציאה בסיבה, ולא נמדד לפי מה שיושב ברישום — למעט מקרה אחד: הערך שביקשנו לכתוב כבר רשום בדיוק ככה, ואז אין מה לתקן.
- **`INSTALLER-FIREWALL-001`.** הפקודה מאמתת אחרי המחיקה ש-`show rule` כבר אינו מוצא את החוקים, והדגל נמחק רק כשגם `ShellExec` הצליח וגם קוד היציאה אפס. אחרת נשמר הדגל ומוצגת הודעה. שימו לב שקוד היציאה של `netsh delete` לבדו אינו ראיה — הוא מחזיר 1 גם על חוק שכבר אינו קיים, שהוא בדיוק המצב הרצוי.

### מה לא שונה, ולמה

- **`LAN-BROADCAST-001`.** הנחת ה-`/24` אכן קיימת, אבל המסמך פספס ש-[`send`](../companion/lib/lan_transport.dart) שולח כל הודעה **גם** אל `255.255.255.255`, מהסוקט של אותו כרטיס — וזה בדיוק היעד שמגיע לכל המחשבים בקטע הרשת בלי תלות במסכה. לכן ההשפעה שתוארה ("הודעות לא מגיעות") אינה מתקיימת. מעבר לכך, Dart אינו חושף netmask כלל, והתיקון המוצע דורש FFI או תהליך מערכת נוסף — מחיר גבוה לבעיה שכבר מכוסה.
- **`FIREWALL-001`.** התיאור הטכני מדויק: פעולה שאינה נקראת אינה מזוהה כחסימה. אבל ההמלצה להפוך `unknown` ל"לא מתיר" סותרת החלטה מתועדת בקוד ([`firewall_check.dart`](../companion/lib/firewall_check.dart)) שנולדה מכשל אמיתי בשטח: אזהרת שווא על חומת אש שולחת את המשתמש לחפש במקום הלא נכון, וזה יקר יותר משתיקה. הטסט עם `Aktion` **מתעד** את ההחלטה במפורש, ואינו מנציח באג. תיקון אמיתי כאן דורש מקור נתונים שאינו תלוי שפה (COM API או PowerShell מובנה), וזה שינוי בסדר גודל אחר.

### מה נוסף לבדיקות

`202` → `214` בדיקות עוברות. הנוספות: דחיית `/publish` ו-`/tabs` ממופע שאינו הבעלים (כולל אימות שהמצב המקומי לא נגע ושההחזקה לא נחטפה), קבלת דיווח בלי `instance`, גוף בקשה שעבר את התקרה, מתאם שממשיך לענות אחריו, גוף שאינו מסתיים, שמירות קונפיג מקבילות, היעדר קובץ זמני אחרי שמירה, וכישלון `reg add` בשני הכיוונים.

הפערים שנשארו פתוחים הם אלה שדורשים שני מחשבי Windows אמיתיים: `RISK-BT-001`, `RISK-BT-002` ו-`RISK-BT-003`.
