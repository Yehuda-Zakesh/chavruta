# חיבור מרחוק — בדיקת התאמה לאוצריא והיתכנות

המסמך מתעד על מה נשענת ההחלטה לממש את החיבור המרוחק **בתוך התוסף, בלי
המתאם (EXE)**, מה נבדק בפועל, ומה עוד דורש בדיקה בשני מחשבים.

## הבסיס שנבדק

| מה | ערך |
|----|-----|
| אוצריא המותקנת שמשמשת לבדיקה ולאריזה | `%LOCALAPPDATA%\Programs\Otzaria\otzaria.exe` — **0.9.98+99800** |
| קוד המקור שנקרא | `otzaria/otzaria`, תג `0.9.98+801`, commit `35c39819140625857d4bb7f0e4b02d264dcebcab` (5.10.2026) |
| רשימת ההיתר הרשמית | `plugin_network_allowlist.txt` בענף `dev`; הכתובת נוספה ב-commit `ad82b1425f87` (19.10.2026) כ-`http://` |
| מנוע WebView2 | ‏Runtime 155.0.4283; הבדיקות רצו ב-Edge 155 (אותו מנוע) |

ההתקנה שאליה מפנה `otzaria` ב-PATH היא אחרת: מפעיל
(`%APPDATA%\com.example\launcher_app\...\otzaria.exe`) בגרסה **0.9.96+90960**,
שאינה עומדת ב-`minAppVersion: 0.9.97` של התוסף. **היא אינה משמשת כאן**; האריזה
והבדיקה נעשות מול ההתקנה ב-`Programs\Otzaria`. אין כאן הנחה שיכולת מענף `dev`
קיימת בגרסה המותקנת — כל מה שלמטה נקרא בתג 0.9.98.

## מה ה-SDK מספק (0.9.98)

- **`network.fetchStream`** (`plugin_bridge_adapter.dart`, `_runPluginNetworkFetchStream`):
  HTTP בצד Flutter, בלי CORS. ‏POST עם גוף מחרוזת, `timeoutMs` עד 120,000,
  עד 4 זרמים פתוחים לתוסף, ו-`return()` על האיטרטור מבטל את הבקשה ומסיים המתנה
  פתוחה (`createRpcStream` ב-`plugin_background_host.dart`).
- **הרשאות ויעדים** (`plugin_network_gate.dart`, `plugin_network_access_resolver.dart`):
  יעד באינטרנט דורש `network.access`, `network.enabled`, הצהרה ב-`network.allowlist`
  **וגם** הופעה ברשימת ההיתר הרשמית. ‏`127.0.0.1` מותר לכל פורט עם `network.localhost`
  בלי הרשימה הרשמית. **הרשימה הרשמית נטענת פעם אחת ונשמרת בזיכרון עד סגירת אוצריא** —
  אחרי שהכתובת תאושר צריך להפעיל את אוצריא מחדש.
- **ריצת רקע** (`plugin_lazy_activation_service.dart`): מופע רקע עולה רק עם
  `app.run_on_startup` (כבויה כברירת מחדל). `keepAlive` חל רק עם
  `app.background_keep_alive`; בלעדיו המופע נכבה אחרי 3 דקות **בלי RPC פתוח** —
  ובקשת ההמתנה הפתוחה מול השרת היא RPC פתוח, ולכן גם היא מחזיקה אותו חי.
  שלילת `app.run_on_startup` מכבה את המופע מיד (`removePlugin`).
- **בין מופעים**: אין ב-SDK ערוץ מסרים ואין אירוע שינוי באחסון. ‏`storage.*` הוא
  אחסון מפתח-ערך בלבד, בלי השוואה-והחלפה, ולכן **אינו נעילה**.
- **מקור הדף**: בווינדוס גם הלשונית וגם הרקע נטענים מ-`file://`, באותה סביבת
  WebView2 (`WebViewEnvironmentHolder`).
- `reader.getCurrentState`, `reader.openBook`, `reader.closeTab`, `workspace.*`
  ו-`reader.current_ref_changed` — כבר בשימוש בתוסף, ללא שינוי.

### למה Web Locks ולא אחסון

`storage.get` ואחריו `storage.set` אינם נעילה: שני מופעים קוראים "פנוי" ושניהם
כותבים "שלי". Web Locks מוכרעת בתהליך הדפדפן, אטומית, ומשתחררת לבד כשהדף מת.
כל דפי `file://` חולקים את מנהל הנעילות — כלומר גם תוספים אחרים — ולכן שם
הנעילה נושא את מזהה התוסף, ושום מידע פרטי אינו עובר ב-`BroadcastChannel`
(שמשמש רק ל"נקישה" ריקה). תוסף זדוני יכול לכל היותר להחזיק את הנעילה ולעצור
את הסנכרון; לא לקרוא דבר.

אם `navigator.locks` אינו קיים, המנוע רץ לפי חלוקה קבועה (רקע; לשונית רק בלי
הרשאת רקע). זו נפילה אחורה ולא נעילה, והיא מוצגת בלשונית כ"מצב תאימות".

## ההחלטה: מסלול א' — בתוך התוסף, בלי EXE

כל יכולת חיונית קיימת: HTTP עם המתנה ארוכה וביטול, ריצת רקע, הכרעה אטומית בין
מופעים, וחתימה תואמת. לכן המתאם **לא שונה**, ואין `RelayTransport` ב-Dart.
הלוגיקה של `SyncHub` (שולחן, נוכחות, הדים, מיזוג והתנגשויות) הועברה כמות
שהיא ל-`plugin/js/remote/hub.js`. הפרוטוקול על החוט זהה לזה של המתאם, כך
שמתאם עם תעבורת relay בעתיד יוכל לדבר עם התוסף ישירות.

## מגבלות שנמצאו

- **מצב "מנותק" של אוצריא מסתיר את התוסף** כשההרשאה `network.access` מאושרת
  (`InstalledPlugin.blockedInOfflineMode`). משתמש חיבור ישיר שעובד במצב מנותק
  צריך לכבות **רק** את `network.access` בהגדרות התוסף; `network.localhost` נשאר,
  והחיבור הישיר ממשיך לעבוד. המתג המהיר "גישה לרשת" מכבה את שתיהן יחד — ולכן
  אינו מתאים כאן. בהתקנה במצב מנותק `network.access` מתחילה כבויה ממילא.
- **הכתובת אושרה כ-`http://`** (commit `ad82b14` בענף `dev` של אוצריא,
  19.10.2026), ולכן התוסף פונה ל-`http://chavruta-relay.chavruta.workers.dev`.
  אוצריא משווה את הכתובת כקידומת מלאה כולל ה-scheme, ו-`https://` לא היה מתאים.
  ההודעות חתומות ב-HMAC, ולכן אי אפשר לזייף או לשנות אותן בדרך — אבל הן
  **גלויות** לכל מי שבדרך: שמות ספרים, מקום הלימוד ושם המכשיר (גיבוב החדר היה
  גלוי לשרת בכל מקרה). כשתאושר גם `https://`, מחליפים את `RELAY_URL` ב-
  `remote-link.js` ואת הרשומה במניפסט.
- אוצריא טוענת את רשימת ההיתר פעם אחת בעלייה — **אחרי עדכון הרשימה צריך
  להפעיל את אוצריא מחדש**. גרסה מותקנת שאינה מצליחה למשוך את הרשימה מ-GitHub
  נופלת לעותק שקומפל איתה, ושם הכתובת אינה מופיעה.
- **עלות השרת**: כל לקוח מחזיק בקשת המתנה פתוחה כמעט תמיד, ושולח נוכחות כל 20
  שניות. כדאי לבדוק בלוח הבקרה של Cloudflare את צריכת ה-Durable Objects (משך
  פעילות) לפני הפצה רחבה.

## מה עוד דורש בדיקה בשני מחשבים, בתוך אוצריא

1. התקנת `.otzplugin` ואישור ההרשאות (כולל ריצת רקע).
2. אחרי אישור הכתובת והפעלה מחדש: שני מחשבים ב"חיבור מרחוק" עם אותו קוד —
   נוכחות, מעבר דף, פתיחת ספר בשולחן המשותף, סגירה לפי המדיניות, ספר חסר.
3. סגירת לשונית החברותא וקריאה בספר — שורת האבחון "מסנכרן כעת: מופע הרקע",
   והסנכרון ממשיך.
4. פתיחה וסגירה של הלשונית כמה פעמים — לעולם לא שני מנועים (אין ניווט כפול).
5. שלילת `app.run_on_startup` — הלשונית לוקחת את המנוע. שלילת `network.access` —
   הודעה ברורה, וחזרה לבד כשהיא מודלקת.
6. ניתוק האינטרנט באחד המחשבים וחיבורו מחדש.
7. החלפה בין "חיבור ישיר" ל"חיבור מרחוק" באמצע מפגש, בשני הכיוונים.
8. משתמש קיים (שדרוג מהגרסה הקודמת) — נשאר בחיבור הישיר בלי לגעת בדבר.
